# Вибір тривалості для планування

У формі створення й редагування завдання показується попередній прогноз. Він обчислюється після паузи у введенні (400 мс) без створення запису в базі. Зміна дисципліни, типу, складності, пріоритету та власної оцінки запускає новий розрахунок. Відповіді для застарілих параметрів не відображаються.

POST /api/predictions/preview приймає subjectId, необов’язкові taskId і parentId та input у форматі TaskInput. Права на дисципліну, завдання та батьківський запис перевіряються на сервері. Навчальна історія містить лише завершені завдання поточного користувача; запис, який редагується, виключається. Якщо немає історії й власної оцінки, повертається 204.

TaskInput і TaskView мають поле planningTimeSource:
- USER_ESTIMATE — використовувати estimatedMinutes. Для цього потрібна додатна власна оцінка.
- PREDICTION — використовувати актуальний прогноз, а за його відсутності — власну оцінку.

Власна оцінка estimatedMinutes не замінюється прогнозом. Початкові характеристики навчального прикладу також зберігаються окремо. Вибір джерела використовується в автоматичному розкладі та показниках прогресу аналітики. Витрачений час віднімається від обраної загальної тривалості. Явно заданий початок і завершення ручного заняття залишаються фіксованими.

Міграція V24 додає tasks.planning_time_source. Для наявних записів і запитів без нового поля використовується PREDICTION, що зберігає попередню поведінку. Для вже сформованого розкладу зміни застосовуються під час перерозподілу або автоматичного перепланування, якщо воно ввімкнене.

Перевірено: 97 серверних тестів, 35 клієнтських перевірок, збірка клієнта; браузерний сценарій обчислення прогнозу до збереження, зміни оцінки, збереження та повторного відкриття обох варіантів. Інтеграційний тест перевіряє 30 хв у розкладі за власною оцінкою та 60 хв за прогнозом, збереження оцінки для навчання й обмеження доступу.
