# StudyPlanner

Інформаційна система персоналізованого планування навчальної діяльності: дисципліни, завдання, облік часу, прогнозування тривалості, автоматичний розклад, аналітика та гейміфікація.

## Технології

- Java 21, Spring Boot 4.1.1, Spring Data JPA, Bean Validation.
- React 19, TypeScript, Vite.
- PostgreSQL 17 для основної бази; H2 лише для автоматичних тестів.
- Flyway створює та версіонує схему. Hibernate перевіряє її, а не змінює автоматично.
- Усі прикладні репозиторії розширюють JpaRepository. Додаткові запити визначено через Spring Data JPA та JPQL. Оновлення: `docs/JPA_PERSISTENCE.md`.
- Maven Wrapper входить у проєкт: окремо встановлювати Maven не потрібно.

Контролери серверних модулів розміщені в пакетах `controllers`. Інші основні групи компонентів: `service`, `repository`, `domain` та `dto`.

## Швидкий запуск у Windows

Потрібні JDK 21 та Node.js 20.19+ або 22.12+. Для першого запуску потрібен інтернет для залежностей.

Запусти Docker Desktop. Скрипт `run-backend.cmd` сам запускає PostgreSQL і очікує готовності бази. Відкрий два термінали в корені проєкту:

```powershell
.\run-backend.cmd
```

```powershell
.\run-frontend.cmd
```

Відкрий http://127.0.0.1:5173. Сервер працює на http://127.0.0.1:8080.
Для зупинки натисни Ctrl+C у кожному терміналі. Дані зберігаються в Docker volume PostgreSQL.
Перед запуском переконайся, що попередні процеси не займають порти 8080 та 5173.

## PostgreSQL

Запусти Docker Desktop, потім із кореня проєкту:

```powershell
docker --context desktop-linux compose up -d --wait db
cd backend
.\mvnw.cmd -B -ntp spring-boot:run
```

Інтерфейс запускається тією самою командою `run-frontend.cmd` із кореня.
Конфігурація підтримує `DB_URL`, `DB_USER`, `POSTGRES_PASSWORD`.
Значення пароля за замовчуванням у Compose й Java збігаються та призначені для локальної розробки.
При зміні пароля встанови однакове значення в середовищі обох процесів.
Дані PostgreSQL зберігаються в іменованому Docker volume.
PostgreSQL використовується за замовчуванням. Старий файл H2 збережений як джерело попередніх даних; автоматичного перенесення немає.

## Що вже працює

- Створення й редагування предметів: назва, опис, колір.
- Створення, редагування та видалення задач.
- Статуси «До виконання», «У роботі», «Виконано».
- Пріоритет, дедлайн як календарна дата, оцінка часу у хвилинах.
- Один рівень підзадач із власними характеристиками.
- Лічильник виконаних підзадач; статус батьківської задачі змінюється вручну.
- Пошук у назвах і описах, фільтри статусу та пріоритету в межах вибраного предмета.
- Підсумки основних задач: загальна кількість, виконані й прострочені.
- Підтвердження видалення, перевірки введення та повідомлення про помилки.
- Український адаптивний інтерфейс.
- Загальний місячний календар дедлайнів усіх предметів: перегляд задач дня, перехід між місяцями, створення задачі на дату.
- Задачі без дедлайну в окремому списку під календарем; пошук і фільтри працюють в обох виглядах.

Якщо фільтру відповідає підзадача, відображається вся її група з батьківською задачею для збереження контексту.

## Модель та правила

`Subject` має багато `Task`. Поле `Task.parentTaskId` посилається на батьківську задачу або дорівнює `null`.
Предмет і батьківська задача задаються лише при створенні; зміна цих зв’язків у поточному API не передбачена. Тому цикли створити неможливо.
Сервер перевіряє, що батьківська задача належить тому самому предмету і сама не є підзадачею.
Видалення основної задачі видаляє її підзадачі. Видалення окремої підзадачі не змінює інші.
Архівування відкладено. Усі предмети відображаються в спільному списку та доступні для редагування.
Історичне поле `archived` збережене в базі для сумісності, але не впливає на роботу й не входить до API.
Усі ідентифікатори — UUID, технічні часові мітки — UTC, дедлайн — дата без часу.

## REST API

| Метод | Шлях | Дія |
|---|---|---|
| GET | `/api/subjects` | Усі предмети |
| POST | `/api/subjects` | Створити предмет |
| PUT | `/api/subjects/{id}` | Редагувати предмет |
| GET | `/api/subjects/{id}/tasks` | Задачі та підзадачі предмета |
| POST | `/api/subjects/{id}/tasks` | Створити основну задачу |
| POST | `/api/subjects/{id}/tasks?parentId={uuid}` | Створити підзадачу |
| PUT | `/api/tasks/{id}` | Редагувати характеристики задачі |
| PATCH | `/api/tasks/{id}/status` | Змінити статус |
| DELETE | `/api/tasks/{id}` | Видалити задачу з підзадачами |
| POST | `/api/tasks/{id}/timer/start` | Запустити таймер (одночасно лише один) |
| POST | `/api/tasks/{id}/timer/stop` | Зупинити таймер і зберегти час |
| GET | `/api/tasks/{id}/time-entries` | Записи витраченого часу задачі |
| POST | `/api/tasks/{id}/time-entries` | Додати витрачений час вручну: `{"minutes":45,"date":"2026-10-02"}` |
| DELETE | `/api/time-entries/{id}` | Видалити запис часу |
| GET | `/api/predictions` | Прогноз тривалості всіх невиконаних задач і стан моделі |
| GET | `/api/analytics?from=2026-09-08&to=2026-10-07` | Показники навчальної діяльності за період (без параметрів — останні 30 днів; не більше 366 днів) |

Предмет:

```json
{"name":"Бази даних","description":"Навчальні роботи","color":"#6262d9"}
```

Задача:

```json
{"title":"Лабораторна №1","description":"Спроєктувати таблиці","status":"TODO","priority":"HIGH","dueDate":"2026-10-01","estimatedMinutes":90}
```

`dueDate` і `estimatedMinutes` можуть бути `null`. Опис може бути порожнім рядком.
Статус: `TODO`, `IN_PROGRESS`, `DONE`; пріоритет: `LOW`, `MEDIUM`, `HIGH`.
Запит зміни статусу: `{"status":"DONE"}`.

## Облік часу та прогнозування

Відповіді з задачами містять `actualMinutes` (сума завершених записів) і `timerStartedAt` (початок активного таймера або `null`).
Запуск таймера переводить задачу з `TODO` в `IN_PROGRESS`; завершення задачі автоматично зупиняє її таймер.

Прогноз навчається на завершених задачах із фактичним часом і збереженими початковими характеристиками. Нові задачі зберігають незмінну початкову оцінку, пріоритет, тип і очікувану складність. Редагування завершеної задачі не переписує ці значення. Старі записи збережено, але виключено з навчання: достовірно відновити початкові характеристики неможливо. Мінлива кількість підзадач не використовується як ознака.

Від 8 придатних прикладів використовується ridge-регресія, якщо є також щонайменше 4 приклади відповідного типу (з оцінкою або без неї). За меншої історії застосовується поправка до оцінки або медіана. Без історії повертається власна оцінка, якщо вона задана; інакше прогноз відсутній. Модель навчається при зверненні до сервісу, зокрема під час планування.

Похибка MAPE розраховується за хронологією на момент створення завдання: навчання, історичні ознаки та підбір параметрів використовують лише записи, чиї поточні дані стали доступними раніше. Міграція V23 додає `tasks.prediction_data_at`; позначка оновлюється при зміні завдання та фактичного часу. Старі записи без достовірної позначки залишаються в поточному навчанні, але виключаються з хронологічної перевірки. Це консервативна перевірка знімків початкових характеристик, а не журнал усіх прогнозів: пізніше виправлені записи не відновлюються в попередньому вигляді, а виключаються з раніших навчальних вибірок.

Для регуляризації порівнюються значення 0.1, 1, 3, 10 і 30 за MAPE на максимум 20 останніх придатних хронологічних прикладах, де застосовна регресія. Потрібно щонайменше 3 таких приклади; до цього використовується типове значення 3. Під час оцінювання кожного зовнішнього прикладу підбір виконується заново лише всередині його навчальної історії, без доступу до перевірочного результату. В API повертаються `regularization`, `regularizationTuned` і `tuningSamples`.

Прогноз системи, оцінки користувача та історична медіана порівнюються на однакових прикладах. Якщо є щонайменше 3 перевірочні записи з оцінкою, використовується ця підмножина; інакше порівнюються прогноз і медіана на всіх придатних записах. До накопичення 3 перевірок відсоток похибки не показується. `regressionEvaluationSamples` відокремлює кількість перевірок регресії від резервних способів у спільному показнику якості стратегії.

Усі прогнози позначаються як попередні. Поле `confidence=LOW` збережене для сумісності API; кількість задач більше не підвищує достовірність автоматично. Діапазон часу є орієнтовним, без гарантованого статистичного покриття.

Міграція V4 додає знімки характеристик і спільний рядок блокування таймера. Запуск таймера блокує цей рядок у транзакції, тому одночасні запити для різних предметів не створюють два активні таймери. Наявні записи часу не видаляються. Якщо старі дані вже містять кілька активних таймерів, їх потрібно зупинити звичайними діями інтерфейсу.

## Аналітика навчальної діяльності

Сторінка «Аналітика» (бічне меню) показує за вибраний період (7, 30, 90 днів або довільні дати): кількість виконаних завдань,
фактично витрачений час, дотримання дедлайнів, виконання плану та регулярність. Є графіки динаміки «факт проти плану» за днями
(для періодів понад 31 день — за тижнями), розподіл часу за предметами та днями тижня і прогрес відкритих завдань відносно
прогнозу чи оцінки. Показники повертає `GET /api/analytics`; обчислення виконує чистий клас `AnalyticsCalculator`.

- Час береться лише із завершених сесій (`COMPLETED`), день сесії визначається за часовим поясом планування.
- Дедлайн зараховується «вчасно», якщо завдання завершено не пізніше дати терміну. Дата завершення береться з таблиці нагород;
  для старих завдань без достовірної дати вона невідома, такі завдання лишаються поза відсотком.
- Виконання плану: запланований обсяг — сума запланованих хвилин сесій, час яких минув; виконаний — `min(факт, план)`.
  Скасований завершенням завдання план не вважається пропущеним, а робота понад план і поза планом показується окремо.
- Міграція V13 додає `study_sessions.planned_minutes`: обсяг, запланований до початку роботи, зберігається, коли сесія стає
  таймером чи ручним записом. Минулий автоматичний план при перепланувані тепер позначається `SKIPPED`, а не видаляється,
  щоб пропущена робота лишалася в статистиці. Для старих записів без `planned_minutes` план обчислюється з меж сесії, а для
  вже завершених історичних сесій він невідомий, і вони рахуються як робота поза планом.

## Межі першого етапу

Це локальна однокористувацька версія. Реєстрації, входу та розмежування доступу ще немає.
Наступний етап для багатокористувацької версії: користувачі, власник предмета, автентифікація та перевірка доступу до кожного запиту.
Календар показує дедлайни задач і підзадач. Сповіщення, планування часових блоків, автоматичний розклад і статистика часу поки не реалізовані (облік часу й прогноз тривалості вже є).
Сервер та інтерфейс за замовчуванням слухають лише локальну адресу.
PostgreSQL-конфігурацію підготовлено; поточні автоматичні тести перевіряють H2.


## Автоматичне планування

У загальному календарі відкрийте **Доступний час**, додайте щотижневі проміжки,
задайте часовий пояс, горизонт плану (1–90 днів) і максимальну тривалість сесії
(15–240 хв). Збережіть налаштування та натисніть **Сформувати розклад**.
Відсутність проміжків означає, що автоматично планувати заняття ніде.

Алгоритм бере прогнозовану тривалість, а за відсутності прогнозу — оцінку користувача.
Віднімає зафіксований час і час активного таймера; враховує майбутню частину ручних
і вже розпочатих автоматичних сесій. Розподіляє роботу за найближчим дедлайном,
потім за пріоритетом, розбиваючи її на часові блоки без перетинів.
Ручні заняття не переміщуються. Для батьківського завдання з підзадачами плануються
лише підзадачі; власний час батьківського завдання автоматично не додається.
Недостатня місткість, прострочений дедлайн, відсутня або вичерпана оцінка відображаються
в «Потребують уваги». Завдання не позначається виконаним лише через завершення сесії.

Автоперерозподіл за замовчуванням вимкнений. Після його ввімкнення сервер перевіряє
зміни щохвилини, а відкритий календар — також після редагування завдань. Зміни
характеристик, часу роботи, доступності й зовнішніх подій або пропущена сесія
перебудовують майбутні блоки. Якщо вхідні дані не змінилися, план залишається стабільним.
Вже розпочатий автоматичний блок зберігається до його закінчення.

Міграція V5 додає planning_settings, study_availability, study_sessions,
calendar_events та planning_issues. Вона застосовується Flyway під час запуску сервера.
Це локальна однокористувацька модель; облікові записи та розділення даних за користувачем
потребуватимуть окремого розширення.

### Зовнішні календарі

Підтримується обмін файлами iCalendar (.ics), а не OAuth або фонова синхронізація
Google/Microsoft-акаунтів. Імпортовані події відображаються у тижневій сітці та
блокують час. Повторний імпорт оновлює подію за UID без дублювання. Видалені з файлу
події не видаляються автоматично: їх можна прибрати в інтерфейсі; STATUS:CANCELLED
або TRANSP:TRANSPARENT вилучає відповідний зайнятий блок.
Експортуються автоматичні й ручні навчальні заняття в UTC. Власний експорт повторно
не імпортується як зайнятий час. Експорт — знімок розкладу; зміни після експорту
не надсилаються до зовнішнього календаря автоматично.

Імпорт підтримує окремі події, дати на весь день (кінець невключно), UTC та IANA TZID.
Повторення RRULE/RDATE/EXDATE/RECURRENCE-ID і невідомі часові пояси відхиляються
із повідомленням; частковий імпорт такого файлу не виконується. Ліміт — 1 МБ / 2000 подій.
Формат обміну: https://www.rfc-editor.org/rfc/rfc5545


### Персоналізація часу занять

Міграція V6 додає planning_settings.habit_aware (типово TRUE). У «Доступний час»
можна вимкнути врахування звичних годин. Джерело — лише завершені TIMER-сесії
тривалістю від 5 хв до 8 год за останні 180 днів. Ручні записи з відомою лише датою,
активні та майбутні сесії не використовуються. Потрібні щонайменше 3 різні дні.

Профілі обчислюються в пам’яті для конкретного завдання, предмета та користувача.
Кожен день має один нормований внесок; новіші дні отримують більшу вагу
(період напівзменшення ваги — 45 днів). Оцінка кандидата враховує годину та день тижня.
Достатня історія предмета має вагу 70% проти 30% загальної; достатня історія
конкретного завдання — 60% проти 40% результату предмета/користувача.
За малої історії обирається найближчий доступний час. Тип завдання не аналізується,
бо окремого поля типу в моделі немає.

Переваги ранжують лише вільні допустимі блоки. Дедлайн, зайнятий час, доступність
і збереження ручних занять — обов’язкові обмеження. Пошук звичнішого часу
не відкладає черговий блок більш ніж на 2 дні від найближчого доступного дня.
Це евристика частоти активності, а не модель продуктивності й не глобальна оптимізація.

Прогноз тривалості використовує ridge-регресію та логарифмічне перетворення.
Реалізовано USER_ESTIMATE, порівняння з оцінкою користувача й медіаною,
хронологічну перевірку та підбір регуляризації з вкладеною перевіркою.
Калібрована впевненість не заявляється.

## Навчальні дні та серія активності
У профілі оберіть навчальні дні (типово понеділок–п’ятниця). Серія зростає за завершення хоча б одного нового завдання або підзавдання в навчальний день. Вихідні не збільшують і не переривають серію; бали та календар активності враховують завершення в усі дні. Пропуск навчального дня перериває серію після завершення цього дня в часовому поясі планування. Зміна навчальних днів перераховує поточну та найдовшу серію за всією історією. Міграція V14 додає поле app_users.study_days; додаткових таблиць немає.

## Власник завдання
Після міграції V15 таблиця tasks не містить user_id. Власник визначається через tasks.subject_id → subjects.user_id; запити TaskRepository перевіряють доступ за дисципліною. Складений зовнішній ключ (parent_task_id, subject_id) забороняє підзавдання з іншої дисципліни. Навчальні сесії та проблеми планування зберігають свого користувача; його відповідність власнику завдання перевіряють серверні сервіси. Їхні зовнішні ключі до tasks контролюють існування завдання, але більше не порівнюють власників на рівні БД. Дані завдань і сесій зберігаються; V1–V14 не змінюються.

## Зберігання навчальних днів після V16
Поточне поле — planning_settings.study_days. Міграція V16 переносить вибрані дні з app_users та видаляє дубльоване поле облікового запису. Вибір днів залишається в інтерфейсі профілю; збереження і читання працюють із planning_settings. Це налаштування стріку, незалежне від часових проміжків study_availability.

## Постійні досягнення (V17)
Таблиця user_achievements зберігає user_id, achievement_code та earned_at. Первинний ключ (user_id, achievement_code) запобігає дублюванню. Отримані досягнення не зникають при зміні графіка чи видаленні завдання. V17 переносить підтверджені сповіщеннями досягнення та поточні досягнення за історією винагород. Якщо дата отримання невідома, earned_at залишається NULL. Рівень надалі обчислюється за балами.

## Єдине сховище зовнішніх подій (V18)
Події iCalendar і Google зберігаються в calendar_events. source визначає джерело: ICALENDAR або GOOGLE. Унікальність (user_id, source, external_uid) розділяє однакові зовнішні ідентифікатори. Синхронізація та відключення Google змінюють лише GOOGLE-записи; повторний імпорт .ics оновлює лише ICALENDAR. V18 переносить усі події, зберігає внутрішні ID імпортованих подій та вилучає google_calendar_events. google_calendar_connection залишається окремою таблицею.

Notification preferences are stored in notification_settings (user_id PK/FK); app_users contains account identity and access state. The schema has 13 main tables.

Sessions and planning issues derive ownership through tasks and subjects; neither table stores user_id. One running timer per user is enforced by account locking and a scoped running-session check.

## Останні оновлення інтерфейсу

- Список усіх завдань із сортуванням за дедлайном, статусом і назвою.
- Канбан із перетягуванням завдань між статусами.
- Денний, тижневий і місячний календар; у денному режимі окремо показано дедлайни.
- Заплановані сесії можна перетягувати між годинами й днями. Тривалість зберігається; перенесені сесії закріплюються під час повторного планування.
- У вікні завдання відображаються заплановані й завершені навчальні сесії.
- Компактні форми створення завдання й ручного обліку часу.
- Профіль із досягненнями та налаштуваннями планування.
